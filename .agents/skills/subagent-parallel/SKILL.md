# Subagent 并行策略

多任务交给多个 subagent 并行, 主模型只做编排、审查与提交。

## 模型选择: subagent 用便宜模型

编排者 (主会话模型) 负责拆任务、写清楚边界、最终验收; subagent 用同生态的
便宜/快速档模型。按主模型生态查表:

| 主模型生态 | Subagent 模型 |
| --- | --- |
| GLM | GLM-5.3-Flash |
| Kimi | Kimi 2.8 |
| Claude | Haiku |
| 其他 | 该家族最便宜的一档 |

在 ZCode 中: Agent 工具的 subagent 跟随会话模型, 无法指定; 需要钉模型时用
CreateWorkflow 的 `subagent_model` (如 `account:.../GLM-5.3-Flash`)。

## 派发阈值 (硬性, 不凭感觉)

满足任一条**必须**派 subagent, 主会话不得自己动手做这类工作:

- **调研点 ≥ 2** — 例如一个软件要查多个 OS 的包可用性 (1 软件 × N OS = N 个
  调研 agent), 或一个任务要在多个目标上验证
- **软件包任务 ≥ 2** — 添加/修改多个软件包, 按包拆 agent
- **调研 + 编写 + 验证齐全的完整链路** — 即使只服务一个软件

只有**单点琐碎检查** (改一行、跑一次单测、看一个文件) 才允许主会话直做。
判断口径: 数一下「要做几次独立的调研/安装/验证动作」, ≥2 就派发; 觉得
"任务小不值得派" 不是豁免理由 — 编排成本由模板承担, 不由省略承担。

## 分工边界: 什么派出去, 什么留下

**派给 subagent (便宜模型)** — 执行密集、边界清晰、产出可检验:
- 软件包可用性调研 (容器里 repoquery/policy 实证; 实证表明 Flash 调研可靠,
  五目标 × 多软件的调研从未失手)
- **简单配方编写**: 档案库直装或 npm 一两行的模块段落 (如 gh/fzf 类)
- 容器端安装验证、批量检查

注意: **需要多步判断的编写不要派 Flash** — 实证两次空转 (base 合并 1.5h
零产出、飞书接线 44min 半成品), 病症是读了很多、迟迟不落盘。多文件合并、
桌面应用特殊渠道 (API 取链/包名陷阱)、多段组合的编写归主会话; subagent
的调研产出 + 已落盘的半成品脚本仍可用, 接线由主会话完成代价很低。

**主会话保留 (贵模型)** — 需要全局判断、跨模块影响、不可回退或牵一发动
全身的工作:
- 架构设计与重构 (生成器/库代码、模块体系、目录结构)
- CI / workflow / 测试框架的搭建与修改
- 规范与决策 (选型原则、拆分粒度、优先级裁定)
- **多步判断型编写** (多文件合并、特殊渠道接线 — Flash 空转高发区)
- 最终审查 (diff review)、验收、git 提交推送
- 失败诊断中的根因裁定 (subagent 可以复现现象, 定性归主会话)

## 拆分维度

1. **按软件包拆** — N 个软件包 → N 个 subagent, 各自完成「调研 + 配置 +
   验证」全链路, 互不依赖的包并行跑。
2. **按 OS 拆** — 单个软件要支持多个操作系统时, 每个 OS 一个调研 subagent
   (容器里 `apt-cache policy` / `dnf repoquery` 实证包名与版本), 汇总后再
   写配方。
3. **按任务类型拆** — 调研 / 编写 / 验证 / 验收 交给不同 subagent, 前者
   产出作为后者输入 (新鲜上下文互相审视); 确定性检查 (语法、单测) 不派
   subagent, 直接命令门禁。

## 硬规矩

- **安装与验证行为只能在容器中进行** — subagent 的一切安装/运行/验证命令
  跑在 docker 容器里 (远程测试机 `docker run`), 绝不碰宿主机。容器即用即毁
  (`--rm`) 或命名后必须清理; 管道灌脚本先 `cat > /tmp/x.sh` 物化再执行
  (防交互提示吃掉 stdin)。
- **文件写不交叉** — 每个 subagent 只写自己负责的文件 (一个模块一个 agent),
  避免并发写竞态; 共享文件 (README/tests) 留给编排者或串行阶段。
  **写同一文件的任务禁止并行** — 编排者派发前核对文件集, 重叠即串行
  (后发任务暂存等先发完成, 或合并进同一 workflow 的先后阶段)。「往同一
  模块加两个软件」就是典型: 必须排队, 不能两个 workflow 同时写。
- **ask 自包含** — 每个 subagent 的任务书包含: 仓库位置、规范文件路径、
  远程测试机与容器协议、只许改哪些文件、禁止 git 操作。
- **产出可检验** — subagent 返回结构化结果 (typed), 关键发现须附证据
  (命令与输出), 高危结论由另一个 subagent 独立复核后才采信。

## 典型编排形态

```
调研 (5 agent: 每目标 OS 一个, 容器 repoquery 实证)
  → 编写 (agent: 拿调研结果写配方/模块)
  → 门禁 (命令: validate + 单测 + bash -n, 失败派修复 agent, 有界轮次)
  → 验证 (命令/agent: 容器端到端安装)
  → 汇总报告 (主模型审查 diff、提交)
```
